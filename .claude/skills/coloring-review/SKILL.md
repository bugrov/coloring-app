# Ревью проекта «Раскраска» (Nuxt 4)

Роль: строгий ревьюер. Код в ходе ревью не правишь, пока пользователь не попросит. Результат — отчёт с severity **BLOCKER / MAJOR / MINOR**, ссылкой `file:line`, сутью и способом исправления.

Архитектура и принятые решения описаны в `CLAUDE.md` (и в `docs/PLAN.md`, если он есть). Ревью проверяет код на соответствие этим решениям. Отклонение допустимо, только если оно обосновано и записано в README.

## Выбор режима
- Аргумент `step` или ревью в конце шага: **режим step**.
- Аргумент `full`, «перед сдачей», «готово ли к сдаче»: **режим full**.
- Если аргумента нет: текущая ветка `step-*` означает step, `main` означает full.

---

## Режим step (gate между шагами)
Охват: изменения ветки относительно `main` (`git diff main...HEAD`, `git log main..HEAD`), а также код, который они затрагивают.

1. **Автопроверки** (раздел A). Ошибка любой из них = BLOCKER для шага.
2. **Разделы B–H** применяются только к изменённым файлам.
3. **Чек-лист шага.** Возьми из `CLAUDE.md` (раздел «Шаги MVP») описание текущего шага и для каждого пункта поставь ✅ / ⚠️ / ❌ с доказательством. Отдельно перечисли, что сделано сверх шага, и проверь, согласовано ли это.
4. **Git:** коммиты в формате conventional, нет мусорных коммитов («fix», «wip» без смысла), нет секретов и `.env`.
5. **Отчёт** (формат ниже) + инструкция пользователю: ссылка на PR и preview, 3–6 действий для ручной проверки (с телефона и desktop, если затронут UI), какие решения приняты самостоятельно.
6. **GATE.** Заверши ответ фразой: «Шаг N готов к проверке. Жду твоего ОК, чтобы смержить и перейти к шагу N+1». После этого **ничего не делай**: не мержи, не создавай следующую ветку, не начинай следующий шаг. Продолжать можно только после явного ОК пользователя («ок», «принято», «мержим» и т. п.). Если пришли замечания, исправь их в той же ветке и повтори ревью шага.

Если есть хотя бы один BLOCKER, не предлагай merge: сначала исправление, затем повторное ревью.

## Режим full (перед сдачей)
Все разделы A–J по всему проекту. Отчёт в полном формате.

## A. Автоматические проверки (запусти и покажи краткий вывод)
Пакетный менеджер pnpm. Запускай скрипты из `package.json`; если скрипта нет, это MAJOR.
- typecheck: `pnpm typecheck` (`nuxi typecheck`)
- lint: `pnpm lint` (ESLint, flat config `@nuxt/eslint`)
- стили: `pnpm lint:css` (Stylelint)
- unit: `pnpm test` (Vitest); e2e: `pnpm test:e2e` (Playwright), если шаг затрагивает UI, и всегда в full
- сборка: `pnpm build`
- зависимости: `pnpm audit --prod` (high/critical = MAJOR)
- дубли: `pnpm dlx jscpd app layers shared --min-lines 8 --min-tokens 60 --ignore "**/*.test.ts,**/migrations/**"`
- размер бандла (full и UI-шаги): `pnpm nuxi analyze` или вывод `pnpm build`; сверить с бюджетами из `CLAUDE.md`

## B. Типы и TypeScript
- `strict: true`; нет `any`, `as unknown as`, `@ts-ignore`; `@ts-expect-error` допустим только с комментарием-причиной.
- Доменные типы и zod-схемы лежат в `shared/` и общие для клиента и сервера, не дублируются.
- Все входы API (body, query, params) и пользовательские файлы проходят zod-валидацию на сервере, а не только типизацию.
- Нет неявных `null/undefined` в доменной модели, исчерпывающие `switch` по union-типам.

## C. Архитектура и стиль
- Границы слоёв: `layers/core` не импортирует `layers/coloring` и другие игры, игры не импортируют друг друга. Игра подключается через реестр `defineGame`.
- `layers/coloring/engine` содержит чистый TS: без Vue, Nuxt и DOM-глобалей вне явно переданного canvas. Логику можно тестировать без браузера.
- Движок не реактивный (`markRaw`/`shallowRef`). В горячем цикле рисования нет реактивных записей.
- Компоненты и composables небольшие, с одной ответственностью. Нет мёртвого кода, закомментированных блоков, `console.log`.
- Нет магических чисел (32 цвета, 180°, 95%, 450 мс, 6 px, лимиты SVG): всё вынесено в именованные константы.
- Server routes тонкие: валидация → сервис → ответ. Доступ к БД только через слой `server/db` и сервисы.

## D. Безопасность
- **SVG:** исходная разметка нигде не рендерится (нет `v-html`, `innerHTML`, `<img src=blob:svg>` из пользовательского файла). Отображается только наш нормализованный JSON. Парсер без DTD и entities (XXE и entity-бомбы исключены). Атрибуты `d` проходят whitelist-проверку. Внешние `href`, `<image>`, `<foreignObject>`, `<script>`, `on*` отбрасываются. Лимиты на размер, число элементов и сегментов, таймаут работают. Битый файл даёт понятную ошибку, а не 500.
- **Изоляция пользователей:** каждый запрос к арту, прогрессу, истории и снимку проверяет владельца или назначение (нет IDOR). Есть тест на чужой id.
- **Админка:** `requireAdmin` на каждом `server/api/admin/**`; скрытая страница не считается защитой. Пароль только из env, сравнение защищено от timing-атак.
- **Ввод:** username и страна валидируются (длина, алфавит, ISO-код), запросы параметризованы через Drizzle, нет сырого SQL с интерполяцией.
- **Rate limit** на вход и на запись истории.
- **Cookie сессии:** httpOnly, secure, sameSite. Заголовки `nuxt-security` (CSP без `unsafe-eval`, лимит размера тела).
- **Секреты:** только в env; есть `.env.example`; в истории git нет секретов (`git log -p | grep -iE "secret|token|password|DATABASE_URL"`).

## E. Производительность
- Анимации идут только по `transform`/`opacity`; нет анимации layout-свойств (`width`, `height`, `top`, `left`, `margin`).
- В простое нет постоянного `requestAnimationFrame`, `setInterval` и наблюдателей. Слушатели снимаются при unmount.
- Рисование: батчинг в `rAF`, `getCoalescedEvents` с fallback. Hit-test O(1) по карте меток. Прогресс считается инкрементально по dirty-rect, без полного пересчёта.
- Длинная история: стоимость undo/redo ограничена чекпоинтами. Тест на 1000 операций (undo ≤ 16 мс). Память не растёт линейно с историей.
- DPR холстов ≤ 2 на телефонах. Offscreen-canvas освобождаются.
- Движок и админка загружаются лениво. Бюджет начального JS из `CLAUDE.md` соблюдён. Изображения в галерее с `loading="lazy"` и фиксированным aspect-ratio (нет CLS).
- Галерея использует keyset-пагинацию, без `OFFSET`; есть индексы под запросы.

## F. Надёжность и данные
- Офлайн-очередь операций (IndexedDB), идемпотентность по `(progress_id, seq)`, retry с backoff, видимый индикатор состояния, `beforeunload` при непустой очереди.
- Конфликт вкладок: 409 → состояние перезагружается без потери и без порчи данных.
- Миграции Drizzle есть в репозитории и воспроизводимы. Сиды идемпотентны.
- Ошибки API отдаются в едином формате, клиент показывает понятное сообщение.

## G. Дублирование
- Отчёт jscpd + ручной просмотр: hit-test, расчёт процента, работа с историей, обработчики pointer-событий, проверки доступа, обработка ошибок fetch.

## H. Визуал, UX, mobile-first, a11y
Проверяй через Playwright или `claude-in-chrome`; сравнение с Figma делай через Figma MCP, если он подключён.
- Размеры: 667×375, 844×390, 932×430 (телефоны в альбомной), 375×667 (портрет: экран «Поверните устройство»), 1024×768 и 768×1024 (планшет), 1440×900 (desktop).
- Mobile-first: базовые стили для телефона, нет `max-width`-медиа (grep). Расширение идёт через `min-width` и container queries.
- Игровой режим: `user-select:none`, `-webkit-touch-callout:none`, `touch-action:none` на холсте, нет pull-to-refresh, pinch-zoom страницы и прокрутки (`overscroll-behavior`, `100dvh`), нет контекстного меню на long-press, `viewport-fit=cover`, `safe-area-inset-*` со всех четырёх сторон.
- Панели: смена инструмента анимирует перестройку; при открытии цветов инструменты скрываются, карандаши появляются последовательно; выбор применяется мгновенно, анимация ввод не блокирует.
- Рамка прогресса стартует с 180° и идёт против часовой, корректна при разных пропорциях (карточки и рабочая область).
- Галерея при 0, 1, 3 и 10+ артах; есть состояния загрузки, пустое и ошибочное.
- Ввод мышью, касанием и пером; нет залипания при быстром движении; zoom/pan двумя пальцами не рисует.
- `prefers-reduced-motion`: анимации сокращены, встряска заменена.
- a11y: `aria-label` у инструментов и цветов, видимый focus, touch-цели ≥ 44 px, горячие клавиши undo/redo на desktop.

## I. Чек-лист ТЗ (для каждого пункта ✅ / ⚠️ частично / ❌ нет, с доказательством)
Пользователь и сессия

- [ ] прогресс на карточке, голубая рамка с 180° против часовой

## J. Готовность к устной приёмке (только full)
Для 5 ключевых мест (импорт SVG, определение сегмента под курсором, история и undo, синхронизация с сервером, права в админке) выведи: файл, 3–4 предложения «как это работает и почему так», один вероятный вопрос техлида и короткий ответ на него. Отдельно перечисли участки, которые выглядят сгенерированными и плохо читаются: их нужно разобрать вручную или упростить (кандидаты для `simplify` / `code-simplifier`). Проверь сценарий приёмки: вход → импорт чужого SVG → раскраска → перезагрузка посреди работы → undo/redo → 100% → экспорт → просмотр в админке.

## Какие инструменты использовать при ревью
- Безопасность: `security-review`, `api-security-hardening`.
- Код: `code-review`, агент `feature-dev:code-reviewer`; упрощение: `simplify`, агент `code-simplifier`.
- Производительность и гидрация: агент `nuxt-v4:nuxt-performance-analyzer`, `nuxt-v4:nuxt-production`.
- Визуал и e2e: `playwright`, `example-skills:webapp-testing`, `claude-in-chrome`; сверка с макетом через Figma MCP.
- Деплой и preview: `vercel:vercel-cli`, `vercel:deployments-cicd`.

## Формат отчёта
1. **Итог:** step — «шаг N: готов к проверке / нужны исправления»; full — «готово / не готово к сдаче». Счётчик BLOCKER / MAJOR / MINOR.
2. **Автопроверки** (таблица: проверка | статус | кратко).
3. **Находки** по разделам B–H: severity, `file:line`, суть, как исправить. Сначала самые серьёзные.
4. **Чек-лист:** step — пункты шага; full — раздел I целиком.
5. step: **как проверить руками** + принятые самостоятельно решения. full: **готовность к приёмке** (раздел J).
6. **Топ-5 действий** по приоритету.
7. step: **GATE**, завершающая фраза и остановка до ОК.
