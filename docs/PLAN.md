# План и статус проекта «Раскраска» (Nuxt 4)

Тестовое задание: детская раскраска (галерея, импорт SVG, раскрашивание по сегментам, история на сервере, аналитика, админка). Этот файл хранит **статус шагов, принятые решения и то, что осталось**; решения по областям (SVG-конвейер, движок, история, сессии, БД, Vercel) и ответы техлида лежат в `docs/ARCHITECTURE.md`, правила работы и стек в `CLAUDE.md`, описание для проверяющего в `README.md`. Если документы расходятся, верны `ARCHITECTURE.md` и `README.md`.

Обновляется в конце каждого шага, до отчёта пользователю.

## 2. Что сделано по шагам (коротко; подробности в `ARCHITECTURE.md`)

- **Шаги 2–3.** Конвейер превращает SVG в собственный формат (`region` и `ink`), исходная разметка нигде не хранится; движок Canvas 2D нереактивный, рисование ограничено маской области, прогресс инкрементальный.
- **Шаг 5.** Галерея на keyset по `seq` (12 на страницу), SSR первой страницы, рамка прогресса из SVG-пути, импорт (лимит 20, rate limit), «Начать заново» создаёт попытку.
- **Шаг 6.** Редактор по макету Figma (мобильный `2:223`, с палитрой `10:911`, десктоп `9:685`); последние три цвета, палитра из 32, прозрачность 100/75/50/25, толщина линии, поздравление при 100 %.
- **Шаг 7.** Журнал шагов на сервере (`history_steps`, атомарное сохранение одной CTE-командой с проверкой `rev`), клиент: `HistoryLog`, `Timeline` (снимки каждые 25 шагов, пиксели последних шагов, бюджет ~48 МБ), `HistorySync` (пачки через 2 с, IndexedDB, ретраи 1–30 с); миниатюры в приватном Vercel Blob; лимит 1500 шагов на попытку.
- **Шаг 8.** Аналитика на сервере (`art_events`: `open`, `start`, `complete`, `restart`, запись через `event.waitUntil`, один раз на попытку); админка: рисунки (загрузка с превью, публикация, назначение по странам и игрокам), статистика с SVG-графиками, игроки с проигрыванием журнала, настройки (допуск «закрашено»).

### Шаг 9 (текущий): что сделано

- **Галерея:** плавное появление картинок, первый ряд грузится сразу, запасные варианты при ошибке; рамка прогресса не прыгает при загрузке на узких экранах; отступы и размеры карточек по макету.

- **Макет Figma сверен по координатам** (кадры 1320×1024 и 844×390): карточка редактора на больших экранах, камера-облако, плашка undo/redo 184×56 и 221×75, колонка инструментов (карандаш и ластик из макета, зазоры 2 px, `overflow: clip` вместо сдвигающегося `hidden`), галерея (отступы 24, центр по вертикали). ## 3. Принятые решения и допущения

- **Игрок и ник:** пара (ник, страна), вход без пароля; допустимы латиница, кириллица, цифры, `_` и `-` (3–20 символов), смешивать алфавиты нельзя.
- **Рамка прогресса:** старт слева (180°), заполнение по часовой (после ревью шага 6; изначально против часовой).
- **Портрет:** на сенсорных устройствах экран «Поверните устройство» (ответ техлида).
- **Допуск «закрашено»** глобальный, 95 % по умолчанию, меняется в админке (применяется при следующем открытии рисунка).
- **Лимит undo** 100 шагов, журнал на сервере до 1500 шагов на попытку.
- **Конфликт вкладок:** свои неотправленные шаги дописываются поверх версии сервера, ничего не теряется.
- **База и авторизация:** только документированные решения; к настоящей базе (миграции, сид, e2e с базой) обращаемся только с подтверждения пользователя; тесты сервера идут на PGlite.
- **Конфигурация:** `process.env` только для `DATABASE_URL` и скрипта сида, остальное через `runtimeConfig`.
- **Базовые арты:** в макете осьминог растровый, кота и дома нет; осьминог получен трассировкой образца, кот и дом нарисованы в том же стиле.
- **Редактор на большом экране** (от 1000×800) повторяет макет карточкой на голубом фоне; на телефоне и низких окнах занимает весь экран.

## 4. Идеи на будущее (не делаем до сдачи)

- **Снимок + хвост истории:** сервер хранит снимок холста на шаге K, клиент при открытии грузит снимок и последние 100–200 шагов; снимает лимит 1500 шагов и ускоряет открытие. Нужны смещение в `HistoryLog`, выдача «с шага K», тесты конфликтов.
- **Гайд «как играть»:** подсказки по кнопкам, как в мобильных играх (это выбор цвета, это прозрачность, это толщина линии, это «начать заново»…), первый раз при открытии редактора с возможностью пропустить и повторить; отдельно подсказка про перемещение приближенного рисунка двумя пальцами и кнопка «сбросить масштаб».
- **Память на устройствах:** замер, разрешение холста по классу устройства, объединение промежуточных холстов.
- **Временные ссылки на Blob** для миниатюр (напрямую с CDN), если галерея станет медленной.
- **SSR-кеш галереи** сознательно не делаем: данные у каждого игрока свои, выигрыш мал.
- **Тесты:** экспорт PNG и «поделиться», дорисовка до 100 % мышью, реальные файлы из Illustrator и Inkscape.
- Полный список улучшений: README, раздел «Что улучшить».

## 5. Известные мелочи

- Миниатюра кешируется на час (`private, max-age=3600`): исправленный встроенный арт может обновиться не сразу.
- `readRawBody` буферизует тело до проверки размера (ограничено `nuxt-security` и Vercel).
- Лимит 20 импортов может перелетать при параллельных запросах (драйвер Neon HTTP без транзакций).
- В dev-базе лежат тестовые игроки `e2e…`, `vis…` и т. п. (чистим только по просьбе пользователя).
- В истории два коммита с одинаковым сообщением «fix(coloring): размер арта в карточке…» (переписывать не нужно).
- Нестабильный под нагрузкой e2e миниатюры (в одиночку проходит).

## 6. Как работаем

- Цикл шага: ветка `step-N-<name>` от `main` → небольшие коммиты (conventional, по-русски) → typecheck, lint, lint:css, test, build (+ e2e на UI) → `/coloring-review step` → push → ссылка на PR → **стоп до явного «ОК»** → merge без squash → обновить этот файл и `ARCHITECTURE.md`.
- Ревью шага: свой чек-лист, `code-review`, `code-simplifier` (на больших шагах), `security-review` (ввод, файлы, сервер, права). Находки исправляем в той же ветке, MINOR записываем.
- Перед сдачей: `/coloring-review full` (раздел «Результаты проверок» выше).
- Старт новой сессии: прочитать `CLAUDE.md` и этот файл, затем `docs/ARCHITECTURE.md` по области работы.
