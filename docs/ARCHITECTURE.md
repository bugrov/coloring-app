# Архитектура и решения (подробности)

Вынесено из `CLAUDE.md`, чтобы тот не оплачивался на каждом ходу. Читать, когда трогаешь соответствующую область: SVG, движок, история, вход и сессии, БД, деплой. Когда решение меняется, правим здесь и в `docs/PLAN.md` (раздел 0).

## Сессии, безопасность, БД, Vercel
- **Сессии:** `nuxt-auth-utils`: шифрованная cookie (`httpOnly`, `secure`, `sameSite=lax`), пароль `NUXT_SESSION_PASSWORD` ≥ 32 символов, срок жизни 30 дней. В `user` лежит то, что видит клиент, в `secure` (только сервер) роль, которой доверяет сервер. Вход заменяет сессию целиком (`replaceUserSession`), выход и чтение сессии на клиенте даёт сам модуль (`useUserSession`, `/api/_auth/session`, этот путь нельзя перехватывать middleware).
- **Заголовки безопасности:** `nuxt-security` (CSP с nonce, HSTS, `X-Frame-Options` и др. по умолчанию). Его rate limiter хранит счётчики в памяти одного экземпляра сервера и по документации не годится для сложного продакшена: включён только для маршрутов входа (пользователь 60 за 5 мин с IP, админ 5 за 5 мин), надёжный вариант — внешнее хранилище. Клиент определяется по `x-forwarded-for` (на Vercel его выставляет платформа). XSS-валидатор по умолчанию проверяет тела POST и заблокирует загрузку SVG: для маршрутов импорта (шаги 5 и 8) его отключаем через `routeRules`.
- **Временное закрепление `xss@1.0.15`** в `pnpm-workspace.yaml`: `nuxt-security` 2.6.0 с `xss` 1.0.16 падает (`escapeHtml is not a function`, каждый POST даёт 500), исправление ждёт слияния ([PR #765](https://github.com/Baroshem/nuxt-security/pull/765)). Снять закрепление, когда выйдет версия с поддержкой.
- **Миграции применяются в сборке Vercel:** `vercel.json` → `buildCommand: "pnpm db:migrate && pnpm build"` (документированный способ интеграции Neon: превью получает схему в своей ветке БД, продакшен — в `main`). Упавшая миграция останавливает деплой. Поэтому **миграции обратно совместимы с предыдущей версией кода**: только добавляем (новые таблицы, колонки с default или nullable); удаление и переименование делаем в два деплоя.
- **Переменные Vercel:** интеграция Neon сама создаёт `DATABASE_URL` и `DATABASE_URL_UNPOOLED`. Вручную для Production и Preview: `NUXT_SESSION_PASSWORD` (≥ 32 символов, свой для каждого окружения), `NUXT_ADMIN_LOGIN`, `NUXT_ADMIN_PASSWORD`.
- **Конфигурация сервера через `runtimeConfig`** (документация Nuxt): ключи объявлены в `nuxt.config`, значения подставляются переменными `NUXT_<КЛЮЧ>`, читаются через `useRuntimeConfig(event)`. Nuxt приводит значения к типам (`destr`): пароль вида `4848e0` придёт числом, поэтому не-строка считается «не настроено» и вход отключается. Исключение — `DATABASE_URL`: его имя задаёт интеграция Neon, а `runtimeConfig` с другим именем переменной ломается в рантайме, поэтому он читается из `process.env`.
- **Журнал безопасности:** `layers/core/server/utils/audit.ts` пишет одну JSON-строку на событие (вход администратора: успех, отказ, не настроен) с адресом и временем, без введённого пользователем. `nuxt-security` по умолчанию вырезает весь `console` из сборки, поэтому `removeLoggers: false`, а правило ESLint `no-console` не пускает логи куда-либо ещё.
- **Drizzle:** стабильная ветка `latest` (0.45), документация описывает RC 1.0, используемые вызовы совпадают. Драйвер `neon-http` не поддерживает интерактивные транзакции, поэтому сервисы используют одиночные запросы. Приложение работает через pooled `DATABASE_URL`, миграции через прямой `DATABASE_URL_UNPOOLED` (требование Neon). `.env` в `drizzle-kit` подаёт Node (`--env-file-if-exists=.env`), без `dotenv`.

## Ключевые решения по областям
**SVG-конвейер** (одинаков для импорта пользователем и для админки, выполняется на сервере):
- Лимиты: ≤ 1 МБ, ≤ 3000 элементов, ≤ 500 регионов, ≤ 3000 элементов результата и ≤ 2 МБ path-данных, CSS ≤ 64 КБ, вложенность ≤ 256, обходы с `<use>` ≤ 20 × элементов, обработанные path-данные ≤ 2 × размера файла + 64 КБ, результат ≤ 4 × размера файла + 64 КБ, viewBox в разумных пределах (соотношение сторон ≤ 20), таймаут 2 с. `@xmldom/xmldom` без DTD и entities. Разбор CSS — линейный сканер, без регулярок по недоверенному тексту. Детали предупреждений очищены до безопасного алфавита.
- **Рисунки из одних тёмных заливок** (шаг 9, `shared/svg/regions.ts`): если областей не нашлось, а `ink` есть, линии растеризуются (свои сканлайн-заливка по nonzero и evenodd, кривые режутся на отрезки, обводка как прямоугольники с квадратными концами) в растр 1024 px по длинной стороне, линии утолщаются на 1 px (закрыть щели), связные пустые участки (четырёхсвязная заливка) крупнее порога становятся областями; участок, достающий до края листа, остаётся фоном, если он один, а если лист разделён линиями на несколько больших частей (вторая по величине не меньше 3 % растра, `SYNTH_DIVIDED_SHARE`), каждая такая часть тоже область; контур участка (расширенного на 2 px, чтобы уйти под линию) берётся обходом границы пикселей, упрощается Дугласом-Пекером (0,9 px) и записывается как `M…L…Z`. Области кладутся в начало списка (под линии). Время и размер результата в общих лимитах (2 с, 2 МБ, 3000 элементов, 500 областей, берутся самые крупные).
- **Фон.** Фоном (заливка фрейма Figma) считается только простой прямоугольник на весь холст (тег `rect` или путь из прямых команд, не больше 8): большой тёмный контур с кривыми, занимающий весь рисунок, это линии, а не фон (раньше такой контур принимался за фон и пропадал из картинки).
- **Заголовок документа:** `withoutPlainDoctype` вырезает `DOCTYPE` без внутреннего блока; внутренний блок, любой `<!ENTITY`, второй `DOCTYPE` и незакрытый заголовок отклоняются (`doctype-not-allowed`).
- **Для сервера (шаги 4–5):** rate limit на импорт и загрузку в админке (неудачные попытки тоже стоят CPU), загрузку декодировать через `new TextDecoder('utf-8', { fatal: true })` и отклонять не-UTF-8.
- `transform` разбирается своим линейным парсером в матрицу (один раз на элемент), path-данные — своим линейным токенизатором в явные команды, затем один проход `svgpath` на фигуру. Регулярки и неявные повторы `svgpath` на недоверенных данных квадратичны, поэтому их не используем. Выход `d` всегда с явными командами.
- Фигуры → `d`, transform запекаются. Светлые заливки и замкнутые контуры без заливки становятся **регионами** (`region`), тёмные заливки (яркость ≤ 0.2) и все обводки становятся **ink**. Первая фигура на весь холст (заливка фрейма Figma) превращается в регион-фон, а если её нет, фон синтезируется из viewBox. Учитываем `fill-rule="evenodd"`, CSS-классы из `<style>`, игнорируем clipPath фрейма Figma, разворачиваем только локальные `<use>`.
- **Исходная разметка SVG не рендерится никогда.** Храним нормализованный JSON `{version, viewBox, items[]}` (`layers/coloring/shared/art/schema.ts`): элементы `region | ink` в исходном z-порядке, `d` проверяется по whitelist. Формат версии 2: у регионов хранятся `bounds` (считаются при импорте, округлены наружу, проверяется `min ≤ max`), поэтому клиент пути не разбирает и `svgpath` в бандл движка не попадает.
- **Рендер:** арт (регионы белые, ink в своих цветах, исходный порядок) рисуется один раз и накладывается на слой краски через `multiply`. Поэтому контур всегда поверх краски без потери z-порядка и без швов.
- **Ограничение:** регион задаёт замкнутая фигура. Линии, которые визуально делят фигуру, отдельных регионов не создают (нужен flood-fill по растру). Записать в README.
- Проверить конвейер вручную можно на странице `/coloring/lab`.
- Неподдерживаемое (text, image, градиенты, маски, фильтры) пропускаем с предупреждением. Если сегментов 0, показываем понятную ошибку.

**Движок** (Canvas 2D, `layers/coloring/app/engine/`, только клиент; чистая логика вынесена в модули без DOM и покрыта юнит-тестами):
- Слои: paint-канвас (краска на белом фоне контента) и арт поверх (`ArtPreview`, вектор) с `mix-blend-mode: multiply` + `isolation: isolate`.
- Разрешение paint фиксированное, `PAINT_LONG_SIDE = 2048` по длинной стороне. От DPR оно не зависит: память предсказуема на iOS, зум до ~2× остаётся чётким, экспорт идёт тем же разрешением.
- Хит-тест: `isPointInPath` по регионам сверху вниз с префильтром по bbox, только на `pointerdown`. Ink для попадания прозрачен.
- Штрих ограничен **маской региона**: регион минус регионы выше по z-order. Кеш на 2 маски (LRU): чаще всего чередуются объект и фон, а маска фона самая дорогая. Каждый фрагмент рисуется на scratch-канвас, умножается на маску (`destination-in`) и только потом композится в paint (резинка через `destination-out`). Линия физически не выходит из региона.
- Операции хранятся в целочисленной сетке `OP_GRID = 4096` по длинной стороне арта (`layers/coloring/shared/ops`). Формат не зависит от разрешения рендера.
- Pointer Events + `getCoalescedEvents` + батчинг в `rAF`. В простое `rAF` не работает. Нажатия на пустые полосы вокруг рисунка игнорируются, повторы одной точки отбрасываются. Без постоянного `will-change: transform` на контенте, иначе вектор размывается при зуме.
- Удержание: 450 мс, допуск 6 px; заливает или очищает регион. Второй палец включает pinch/pan, Ctrl+колесо и pinch тачпадом дают зум (шаг колеса ограничен, щелчок ≈ ×1.28), колесо при зуме двигает арт.
- Незавершённый штрих (второй палец, `pointercancel`): короткий откатывается из бэкапа региона, очень длинный (уже разрезанный на операции) сохраняется целиком. При смене арта или размонтировании штрих просто выбрасывается.
- Перо: пока рисует перо, касания пальцами игнорируются; касание пером сбрасывает уже лежащие пальцы (ладонь).
- Потерянные `pointerup`: `lostpointercapture` самой сцены обрабатывается как отмена (событие всплывает, поэтому цель проверяется); новый primary-указатель сбрасывает все зависшие, а начатый штрих сохраняет; повторное нажатие тем же указателем сначала коммитит прежний штрих.
- Карандаш: тонкий, **непрозрачная** зернистая текстура (`createPattern`, детерминированный шум, осветление к белому). Непрозрачность важна: перекрытия штриха не темнеют. Кисть: широкая, мягкий край (штампы радиального градиента с шагом по длине, `StampWalker` переносит остаток между фрагментами).
- **Прогресс**: сетка ~256 по длинной стороне. Карта меток (`Int32Array`) рисуется один раз (регионы кодами-хешами, ink поверх как «нет региона» с теми же lineCap/lineJoin, что и экспорт), поэтому под глазами и контурами ничего не считается. Обновление идёт только по dirty-rect штриха: ячейка закрашена, если закрашена хотя бы половина из 16 пикселей-образцов её блока 8×8 (считаем сами по `getImageData`, а не уменьшением через `drawImage`, фильтрация которого отличается в браузерах). Регион засчитывается при покрытии ≥ 95%, 100% показывается только когда готовы все. Фон в прогресс не входит.
- Replay совпадает с живым рисованием: линейные инструменты каждый кадр восстанавливают основу из бэкапа и перерисовывают путь в dirty-rect (только сегменты рядом с ним, поэтому кадр не дорожает с длиной штриха), кисть переносит шаг штампов, длинные штрихи режутся на операции прямо во время рисования. Путь с ошибкой сохраняет валидную часть до неё (как в браузерах). Остаются только различия в сглаживании кромки (альфа ±2–60 на крайних пикселях, их растеризует Skia), визуально незаметно.
- Движок освобождает offscreen-канвасы (`dispose()`) при смене арта и размонтировании. Холсты экспорта живут только на время экспорта.
- Замер: кадр рисования в среднем 0.2 мс на GPU (бюджет 8 мс). Проверочная страница `/coloring/sandbox`.

**История и синхронизация** (шаг 7; код: `layers/coloring/shared/history/`, `app/engine/timeline.ts`, `app/sync/`, `app/composables/useEditorHistory.ts`, `server/services/history.ts`):
- **Журнал шагов.** Шаг = одно действие игрока = массив операций `stroke | fill | clear` (≤ 64 операций, длинный штрих режется по 2000 точек). Новый шаг после undo отрезает ветку redo. Лимит undo `UNDO_LIMIT = 100` (от конца журнала), журнал на сервере хранит всё, до `MAX_HISTORY_STEPS = 1500` шагов за попытку.
- **Сервер.** `history_steps(progress_id, seq, ops jsonb)` с ключом `(progress_id, seq)`; в `progress` добавлены `cursor`, `step_count`, `rev`, `thumbnail_at`. `GET .../history` отдаёт последнюю попытку со всеми шагами одним SELECT (шаги, `rev` и `cursor` согласованы). `PUT .../history` принимает `{attempt, rev, keep, steps, cursor, percent}` («оставь первые keep шагов, замени остальные, поставь курсор»): **один SQL-запрос с data-modifying CTE** (UPDATE `progress ... WHERE rev = $rev AND step_count >= $keep`, затем INSERT ... ON CONFLICT DO UPDATE шагов и DELETE хвоста). Это единственный способ получить атомарность на драйвере `neon-http`, где нет интерактивных транзакций; запрос пишется целиком или не пишется. Нет совпадения `rev`, попытки или `keep` больше числа шагов = 409 `history_conflict`. Попытка создаётся первым сохранением (клиент шлёт `attempt: 0`). Регионы операций проверяются по арту (422), тело по zod-схеме, на маршрут rate limit 1200/мин и отключён `xssValidator` (только числа и цвета).
- **Клиентская модель** `HistoryLog` (чистый TS в `shared`): шаги, курсор, `confirmed` (сколько шагов с начала точно совпадают с сервером), `nextSave()` (пачка ≤ 100 шагов и ≤ 900 КБ), `accepted()`, `failed()`, `reconcile(server)`, `restore(server, unsent)`, `unsent` (для IndexedDB). Покрыта юнит-тестами.
- **Картинка и история вместе** (`Timeline`, фабрика над `PaintHost`): (а) для последних шагов хранятся **пиксели, которые шаг закрыл** (`PaintDelta`: кусок холста по рамке штриха или области заливки, снимается перед применением; `Painter.swapRect` обменивает его с холстом, повторный обмен делает redo), бюджет ~12 млн пикселей (48 МБ), вытесняются самые старые; при открытии истории они снимаются для последних 100 шагов; (б) каждые `CHECKPOINT_EVERY = 25` шагов снимок всего холста вместе со счётчиками прогресса, только в окне отмены (≤ 5 штук). Отмена шага с куском это обмен без повтора (~1 мс), без куска это восстановление снимка и < 25 шагов повтора. Память не растёт с длиной истории. Прогресс измеряется один раз на пачку применённых шагов (`settle`).
- **Фоновое сохранение** (`HistorySync`, без Vue): `changed()` ставит таймер 2 с (≤ 10 с от первого изменения, сразу при 10 неотправленных шагах); одна отправка за раз; отказ сети = статус `offline` и повтор с паузой 1, 2, 4 … 30 с (и сразу по `online`); отказ сервера 401/403/404/413/422 = `failed` без повторов; 409 = чтение версии сервера и `reconcile`, не больше 5 подряд. Неотправленное пишется в IndexedDB (`outbox`, через 300 мс после изменения, при скрытии страницы и при сбоях; чистится после успешного сохранения). Статус в сторе: `saved | saving | offline | failed`.
- **Конфликт** (две вкладки, два устройства): клиент берёт версию сервера и **дописывает неотправленные локальные шаги сверху** (только применённые шаги сервера, ветка redo сервера отрезается). Повторная отправка уже принятого сохранения распознаётся (шаги совпадают) и не дублируется. Чужая новая попытка («Начать заново» в другом окне) отбрасывает локальные шаги старой.
- **Открытие арта**: `GET history` + `outbox.read` → `HistoryLog.restore` (то же, что `reconcile`: работа из прошлого визита не теряется, если сервер ушёл вперёд, шаги ложатся сверху, если шаги уже на сервере, повторно не добавляются) → `Timeline.open` проигрывает журнал кусками по 25 шагов с паузами. Пока идёт открытие, рисовать нельзя (`locked`), индикатор не показан.
- **Уход со страницы**: `visibilitychange` (hidden) и `pagehide` пишут в outbox и пытаются отправить; `beforeunload` предупреждает о несохранённом; выход из редактора на маршруте ждёт досылки и миниатюры ≤ 2 с.
- **«Начать заново»**: досылка несохранённого, `POST restart` (новая попытка, если в текущей есть закрашенное **или шаги**), загрузка пустой истории новой попытки, очистка outbox.
- **Миниатюры**: клиент рисует WebP 512 px (`exportThumbnail`: арт из векторов в этом размере, краска сжимается), `PUT .../thumbnail` (тип проверяется по сигнатуре, ≤ 200 КБ, rate limit), файл в **приватный Vercel Blob** (`thumbnails/<progress id>`), `GET` отдаёт поток после проверки владельца (`private, max-age=86400`, URL с `?v=<thumbnail_at>`). Блок `useThumbnailStore` (`server/utils`): Vercel Blob при `BLOB_STORE_ID`, в разработке без него хранилище в памяти, в проде без хранилища 503. Читается только миниатюра последней попытки. Удаление импорта удаляет файлы.
- Замеры (Chromium без GPU, в e2e `history.spec.ts`): отмена/возврат шагов, нарисованных в сессии, в среднем ~1 мс; шаги из загруженного журнала при бюджете, занятом крупными областями, 25–40 мс; открытие журнала из 1000 крупных штрихов около 10 с. Бюджет «undo ≤ 16 мс на истории 1000 операций» выполняется для свежих шагов; для давних на слабом железе возможны превышения (записано в ограничения).
- «Начать заново» создаёт новую попытку (`progress.attempt`), старая сохраняется вместе с журналом.

**Пользователи и админ:**
- Уникальна **пара (username без учёта регистра, страна)** (ответ техлида): тот же ник в другой стране — другой игрок, ошибки «ник занят» нет, в БД unique `(username_key, country)`. Разрешены латиница A–Z, кириллица, цифры, «_» и «-», 3–20 символов, **латиница и кириллица в одном имени не смешиваются** (иначе `Аnna` с кириллической «А» подделывает `Anna`). В ключе уникальности «ё» равна «е», отображаемое имя остаётся как введено. Остальные письменности и диакритика отклоняются: имя можно записать латиницей.
- Вход в админку по одному логину и паролю из env. Каждый admin-эндпоинт проверяет `requireAdmin` на сервере.
- Все запросы к артам, прогрессу и истории проверяют владельца (IDOR).
- Лимит 20 импортов на пользователя.

**Аналитика и админка** (шаг 8; код: `layers/coloring/server/{services,api/admin/coloring}`, `layers/coloring/shared/admin/`, страницы `layers/coloring/app/pages/admin/coloring/`, оболочка `layers/core/app/components/admin/AdminPage.vue`):
- **События.** Таблица `art_events(type, user_id, art_id, attempt, country, created_at)` в слое игры (события про арты; core о них не знает). Пишет сервер, клиентского кода аналитики нет: `open` при загрузке истории (`GET .../history`), `start` при первом принятом сохранении попытки с шагами (`rev === 1`), `complete` при сохранении с процентом 100, `restart` когда «Начать заново» создало попытку. `start` и `complete` один раз на попытку: частичный уникальный индекс `(user_id, art_id, attempt, type) WHERE type IN ('start','complete')`, повтор отклоняет БД (`ON CONFLICT DO NOTHING`). Сбой записи события глотается (`recordEvent`), запрос игрока не ломается. Страна берётся из сессии на момент события. Сторонних трекеров нет.
- **Публикация и назначение.** `arts.status` (`draft | published | hidden`) и `arts.source` (`builtin | user | admin`); таблица `art_assignments(art_id, country | user_id)` (ровно одно из двух, `CHECK`, уникальные частичные индексы). Видимость (`visibleTo` в `services/arts.ts`): импорт только владельцу; встроенный или админский арт, если он опубликован и либо без назначений (виден всем), либо назначен стране или игроку игрока. Страна игрока берётся подзапросом по `users`, поэтому сигнатуры сервисов не менялись. Загрузка админа создаётся черновиком. Встроенные арты скрываются, не удаляются (сид вернёт их, но не трогает статус).
- **Назначения** заменяются одной командой с двумя CTE (добавить новые `ON CONFLICT DO NOTHING`, удалить не вошедшие), потому что у драйвера neon-http нет транзакций и арт не должен на мгновение открыться всем. Списки передаются JSON-ом: массив JS в `sql` шаблоне drizzle раскрывается в отдельные параметры, а не в массив.
- **API админки** `/api/admin/coloring/*`: `arts` (список со счётчиками и назначениями, загрузка SVG, `[id]` GET/PATCH/DELETE, `[id]/assignments` PUT), `stats?days=`, `players?query=`, `players/:id/arts`, `players/:id/arts/:artId?attempt=` (арт и весь журнал попытки для проигрывания), `settings` GET/PUT. Каждый обработчик начинается с `requireAdmin` (e2e проверяет 401 без сессии и 403 игроку на каждом пути). Загрузка SVG идёт тем же конвейером, что импорт игрока (исходная разметка не хранится), маршруту отключён `xssValidator`. Тела JSON проверяются zod-схемами `shared/admin/schema.ts`.
- **Статистика** (`services/admin-stats.ts`): суммы по типам и число игроков за период, по артам, по дням (`generate_series`, дни без событий включены, UTC), по странам; индексы `(art_id, type, created_at)` и `(created_at)`.
- **Графики** сделаны на SVG и CSS без библиотеки (бандл), по методу скилла dataviz: первые три категориальные цвета проверены валидатором (CVD и контраст; у аквамарина контраст ниже 3:1, поэтому всегда есть легенда, подсказка при наведении и таблица значений), линии 2 px, третья пунктирная (чтобы совпадающие линии не скрывали друг друга), столбцы с закруглённым концом и подписью числа, тёмная схема. Страницы админки без SSR, ленивые чанки.
- **Просмотр состояния игрока**: админ ищет игрока (префикс имени, `%` и `_` экранируются), видит его арты и попытки, а страница `player-art/:playerId/:artId` проигрывает журнал на нередактируемой сцене (`Timeline.load` с курсором шага, ползунок). Только чтение.
- **Палитра.** Хранится в `app_settings` под ключом `palette` (ровно 32 цвета `{hex, name}`, `#rrggbb` в нижнем регистре, без повторов, имя ≤ 30 символов, схема `paletteSchema`); строка, не прошедшая схему, даёт стандартный набор из `shared/palette`. Приходит клиенту в `GET /api/coloring/arts/:id` (`palette`), редактор кладёт её в стор (`editor.palette`), панель и имена цветов читают оттуда. Админка: `GET|PUT /api/admin/coloring/palette`, страница «Палитра».
- **Галерея (шаг 9).** Карточка показывает картинку по цепочке «миниатюра → пустая раскраска (`preview.svg`) → заглушка» (`@error` переключает на следующую), плавно проявляет её по `load` (проверяется и `complete` после гидратации, чтобы закешированная картинка не осталась невидимой), первые `PRIORITY_CARDS = 6` карточек грузят картинку с `loading="eager"` и `fetchpriority="high"`.
- **Настройки.** Таблица `app_settings(key, value jsonb)`; ключи `paintedTolerance` (0.5…1, по умолчанию 0.95) и `palette`. Приходит клиенту в `GET /api/coloring/arts/:id` (`tolerance`) и подставляется в `ProgressTracker`/`computeProgress` вместо константы; значение вне диапазона в БД игнорируется (берётся умолчание).
- **Конфигурация.** Ключ Blob и режим хранилища миниатюр идут через `runtimeConfig` (`blobStoreId` читается из переменной `BLOB_STORE_ID` при сборке конфига, `NUXT_BLOB_STORE_ID` переопределяет в рантайме; `memoryThumbnails` включает хранилище в памяти для разработки и e2e). `process.env` остаётся только для строки БД (`DATABASE_URL`, имя задаёт интеграция Neon) и скрипта сида.

**Экспорт:** картинку собирает движок на offscreen-canvas 2048 px без UI. Blob готовим заранее, потому что Safari требует вызывать `share` синхронно в клике. Если `navigator.share({files})` недоступен, скачиваем файл.

**Редактор** (шаг 6, `layers/coloring/app/{pages/coloring/art,components/editor,stores/editor.ts,composables/useColoringEditor.ts}`):
- Страница `/coloring/art/:artId` тонкая: данные `GET /api/coloring/arts/:id` (`{ id, title, art }`, `private, no-cache`, `Vary: Cookie`, видимость как у `preview.svg`) грузит `useColoringEditor` через `useFetch`; движок живёт в `ColoringStage` (нереактивно), редактор общается с ним событиями `ops`/`progress` и вызовом `replay`.
- Pinia-стор `coloring-editor`: инструмент (по умолчанию кисть), три последних цвета (последний выбран, клик по нему открывает палитру из 32), прозрачность, толщина, прогресс, шаги undo (`Op[][]`, один шаг = одно действие, курсор). Undo/redo сейчас **только в памяти**: `stage.replay(activeOps)`; сохранение, чекпоинты и лимит 100 — шаг 7.
- **Прозрачность** — параметр операции `opacity` (проценты 100/75/50/25, необязательное, у резинки нет; в схеме `stroke` и `fill`). Кисть при `<100%` копит штрих на scratch и каждый кадр перерисовывает поверх бэкапа; маска региона накладывается на копию (`masked`), чтобы мягкий край не умножался (live == replay, есть e2e попиксельно). Порог «закрашено» `PAINTED_ALPHA_MIN = 60`, чтобы засчитывалась и краска 25 %.
- **Толщина** — множитель ширины инструмента `THICKNESS_SCALES = [0.5, 1, 1.8]` (тонкая/средняя/толстая); в операцию пишется итоговая `width`, поэтому формат и replay не менялись.
- Заливка удержанием: оверлей (кольцо 450 мс, затем вспышка цвета 250 мс; при reduced-motion только кольцо) поверх уже закрашенной области, реального «раскрытия краски» нет.
- Рамка прогресса `GalleryProgressFrame` общая у карточек и редактора: старт слева (180°), заполнение **по часовой** (изначально по ТЗ против, изменено по просьбе при проверке шага 6; константа и путь в `utils/progress-frame.ts`). 100%: встряска рамки, карточка «Поздравляем! Рисунок готов» (4,5 с, не перехватывает касания), при reduced-motion свечение и плавное появление.
- Палитра: фокус уходит в список на выбранный цвет, Esc закрывает с любого места, тап вне закрывает и дальше не идёт (не начинает штрих), анимация перестановки карандашей только `transform`/`opacity`.
- Общие SCSS-миксины `plain-button` и `focus-ring` лежат в `layers/core/app/assets/styles/_mixins.scss` и подключены ко всем стилям через `vite.css.preprocessorOptions.scss.additionalData`.
- Плашка undo/redo лежит на нижнем крае белой области по макету; размеры в токенах `--plate-button`, `--plate-pad`, `--plate-height` (`_tokens.scss`: 184×56 на телефоне, 221×75 от 1000 px). Рисунок вписывается выше плашки: `padding-bottom: var(--plate-height)` у `.frame__inner` в `EditorFrame.vue` (откат: убрать эту строку).

## Шаг 9: полировка, изменения в решениях

- **Раскладка редактора.** Страница `/coloring/art/:artId` оборачивает редактор в `.editor-page`: на экранах от 1000 px шириной и 800 px высотой это скруглённая карточка (радиус `--radius-card`) на голубом фоне с полями 20 и 52 px, как в макете, иначе редактор на весь экран. Колонка инструментов использует `overflow: clip` (а не `hidden`): скрытый блок можно прокрутить фокусом, и колонка уезжала вбок при выборе карандаша. Зазор между инструментами `--pencil-gap: 2px`; обёртка `.toolbar__slot` это flex, иначе строчная кнопка добавляет пиксели под каждым карандашом.
- **Галерея.** `--page-gutter` у `SafeAreaPage` (24 px у галереи), сетка по центру по вертикали (`margin: auto` во flex-колонке: длинный список начинается сверху и прокручивается), кнопка «←» в углу страницы от 1000 px и отдельной строкой ниже. Линия прогресса `GalleryProgressFrame` скрыта, пока `ResizeObserver` не измерил карточку: до этого она рисовалась по размеру из макета и «прыгала» на узких экранах.
- **Движок и история.** `Timeline` отменяет начатую перестройку: счётчик `epoch` и флаг `disposed` проверяются после каждой паузы, закрытый таймлайн не трогает холст и не создаёт снимки (раньше запоздалое сохранение после выхода могло перестроить холст другого арта). `HistoryLog.reconcile`: если сервер хранит только префикс локальных шагов (сохранение дошло, ответ потерялся), перестройки нет, обновляются `rev`, `attempt`, `confirmed`. «Начать заново» держит собственный флаг `editor.restarting` (входит в `locked`): конфликт, разрешённый в это время, не снимает блокировку. Во время штриха прямоугольник холста кешируется (`canvasRect`), сбрасывается жестами, колесом и ресайзом.
- **Сервер.** `getRegionIds` (`services/arts.ts`) кеширует id областей арта на инстансе (до 100 артов, TTL 5 минут, порядок по давности использования) для проверки шагов при сохранении истории; проверка видимости арта (`artIsVisible`) идёт раньше и от кеша не зависит. TTL нужен, потому что сид перезаписывает `data` встроенных артов под тем же id. Общий `latestAttempt` в `services/attempts.ts`.
- **Клиент и запросы.** `useApi()` (`core`): `useRequestFetch` с таймаутом 30 с, `useFetch` получают `timeout: API_TIMEOUT_MS`; история и миниатюры имеют свои сигналы на 15 с. При 401 сохранение истории уводит на вход только из текущего редактора, работа остаётся в очереди IndexedDB.
- **Компоненты.** `FormInput`, `FormSelect`, `FormOption` (`core/components/form`), иконки как компоненты (`core/components/icon`), `GameCard` и поля `description`, `cover` у `GameDefinition` (`shared/types/game.ts`, значения задаёт `app.config.ts` игры, обложка лежит в `public` слоя игры). Диалог подтверждения грузится лениво (`LazyConfirmDialog` с `v-if`; открывается в `onMounted`, потому что при создании компонента элемента `<dialog>` ещё нет).
- **Страницы для разработки** (`/coloring/lab`, `/coloring/sandbox`) вызывают `useDevPage()`: в проде 404, если не задан `NUXT_PUBLIC_DEV_PAGES=true` (e2e задаёт его в `playwright.config.ts`).
- **Типы стран.** Запросы используют `z.enum(COUNTRY_CODES)`, ответы `z.string()` (так база и отдаёт); `as unknown as` в схеме больше нет.
- **Индексация.** `public/robots.txt` с `Disallow: /` и глобальный `<meta name="robots" content="noindex, nofollow">` (демо-проект).
- **Стиль кода.** ESLint: `@stylistic/brace-style` в варианте `1tbs`, `curly: multi-line`, пустые строки между логическими блоками (`padding-line-between-statements`).
- **Базовые арты.** Осьминог получен трассировкой растрового образца макета: области (белые компоненты связности, на 2 px заходят под линии) и линии (одна заливка с `evenodd`), `viewBox` 1068×856 с полями как в образце. Кошка и дом без изменений.

## Заметки по шагам (решения техлида и дизайн вперёд)
- Каждая страница объявляет `definePageMeta({ name: ..., auth: ... })` с понятным именем.
- Имена маршрутов лежат в константах: объект `as const` на слой в `layers/<слой>/shared/routes.ts` (не enum). У `core` свои имена (вход, главная, админка), у каждой игры свои: core не импортирует имена игр. Пример: `definePageMeta({ name: CoreRoutes.LOGIN, auth: 'public' })`.
- Имена строчными словами через дефис (`login`, `admin-login`, `coloring-gallery`), как их генерирует Nuxt, чтобы ссылки не ломались.
- Все редиректы, ссылки и `navigateTo` переводим на именованные (`{ name: CoreRoutes.LOGIN }`), строковых путей в коде не остаётся; реестр игр (`GameDefinition.entry`) хранит имя маршрута. Не даём вернуть строковый путь: проверка в ESLint или тест.
- **Ник уникален парой (ник, страна)** (ответ техлида): одинаковый ник в разных странах — разные игроки. Миграция по правилу двух деплоев: добавить составной unique-индекс `(username_key, country)`, в следующем релизе убрать старый unique по `username_key`. `signIn` ищет по паре, `onConflictDoNothing` целится в новый индекс. Ошибка `username_taken`, её сообщение, тесты, e2e и текст в README убираем.
- Заливка удержанием остаётся мгновенной, но с анимацией: кольцо-индикатор у пальца, затем круговое раскрытие цвета ~250 мс; при reduced-motion мгновенно.
- **Прозрачность** (ответ техлида): пресеты 100 / 75 / 50 / 25 %. **Сделано в шаге 6**: кнопка-переключатель в левой колонке (место подтверждено пользователем). Исходная формулировка: пока закладываем кнопку-переключатель; куда её поместить (на панель или в попап) решим позже. Прозрачность — параметр операции (карандаш, кисть, заливка удержанием); штрих рисуется непрозрачным на scratch и композится с `globalAlpha`, поэтому перекрытия внутри одного штриха не темнеют. Резинка стирает полностью. Полупрозрачная краска засчитывается как закрашенная от ≥ 25 % (порог альфы в подсчёте прогресса меняется).
- Лимит undo: константа **100** шагов (`UNDO_LIMIT`), журнал на сервере хранит всё. **Сделано в шаге 7**, замер на 1000 шагов в e2e.
- Синхронизация между устройствами и вкладками: обсуждена с пользователем перед шагом 7 (ответы: при конфликте дописывать свои шаги сверху; хранилище миниатюр Vercel Blob; на сервере все шаги, undo ограничен 100). Реализовано, см. «История и синхронизация».
- Допуск «закрашено» (сейчас 95 %) — глобальная настройка в админке, фолбэк 95 %, если не задана.
- Палитра: по возможности редактируется в админке (опционально).

## Открытые вопросы к техлиду
Пока работаем с принятыми решениями (в скобках — что сделано сейчас). Когда ответ получен, обновляем этот файл и README.

0. **Вход без пароля и защита от подбора:** имя и страна — единственный ключ, лимит по IP слабый (см. README, ограничения). Решения: **PIN или код восстановления** — обсуждаем завтра; **внешний Redis для лимитера** — нет (нет времени), остаётся лимит в памяти; **CSRF-защита входа** (опция `csrf` модуля nuxt-security) — на обсуждение позже. Пока: вход по ТЗ без пароля, лимит в памяти, CSRF нет.
1. **Ник:** уникален глобально или пара «ник + страна»? Устраивает ли, что без пароля ник фактически ключ? (глобально, страна сверяется при входе) **Ответ техлида: пара (ник, страна)** → мини-шаг 4а.
2. **Рамка прогресса:** где точка 180° — слева, сверху или снизу; против часовой — по экрану? (константа, по умолчанию слева) **Ответ: слева (180°), подтверждено.** **Позже изменено: по часовой (просьба при проверке шага 6).**
3. **Прогресс:** по площади или по числу областей, входит ли фон, какой порог «закрашено»? (по площади, фон не входит, порог 95%) **Ответ: допуск — глобальная настройка в админке, фолбэк 95 %** → шаг 8.
4. **Портрет:** допустим экран «Поверните устройство» или нужен адаптив? (экран-заглушка) **Ответ: экран «Поверните устройство» подходит.**
5. **Карандаш и кисть в Unity:** ширина, текстура, прозрачность, нажим пера? (карандаш тонкий с зерном, кисть широкая мягкая, нажим не учитывается)
