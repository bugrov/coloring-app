# Coloring App: веб-раскраска на Nuxt 4

Тестовое задание: детская раскраска (галерея, импорт SVG, раскрашивание по сегментам, история на сервере, аналитика, админка). Срок 3 рабочих дня. Подробный план и обоснования лежат в `docs/PLAN.md`: файл локальный и в git не входит. Если его нет, ориентируемся на этот документ.

Общение с пользователем и тексты коммитов и PR пишем **на русском**. Код, идентификаторы и комментарии в коде пишем на английском.

## Порядок работы (обязательно)
Работаем строго по шагам MVP (список ниже). Каждый шаг проходит один и тот же цикл:
1. Ветка `step-N-<name>` от `main`.
2. Реализация небольшими коммитами (conventional commits: `feat:`, `fix:`, `chore:`, `test:`, `docs:`, `refactor:`).
3. Автопроверки: `pnpm typecheck && pnpm lint && pnpm lint:css && pnpm test && pnpm build`, на UI-шагах ещё `pnpm test:e2e`.
4. Ревью: `/coloring-review step` проводит весь конвейер ревью (см. скилл): свой чек-лист → `code-review` по диффу → агент `code-simplifier` по изменённым файлам → `security-review` на шагах с вводом, файлами, сервером и правами. `security-guidance` (хук) и `typescript-lsp` работают в фоне сами.
5. Push → PR → Vercel preview.
6. **СТОП.** Отчёт пользователю: что сделано, результаты проверок, находки ревью, ссылка на preview, как проверить руками, какие решения приняты.
7. Ждём **явного «ОК»**. Без него не мержим и не начинаем следующий шаг. Замечания исправляем в той же ветке и повторяем пункты 3–6.
8. После ОК: merge без squash (история нужна полная), затем следующий шаг.

Дополнительные правила:
- Неоднозначность, которая не блокирует работу, решаем сами разумным способом и записываем в README («Решения и допущения») и в отчёт шага. Если вопрос блокирует работу, спрашиваем пользователя.
- Не расширяем объём работы шага без согласования. Мелкие находки вне шага записываем в отчёт.
- Секреты храним только в `.env` и в Vercel env. В репозиторий кладём `.env.example`.
- Не пушим в `main` напрямую и не делаем force-push.

## Шаги MVP
0. Подготовка: план, `CLAUDE.md`, скилл ревью, доступ к Figma (MCP), вопросы техлиду.
1. Скелет: Nuxt 4, layers, TS strict, ESLint, Stylelint, Vitest, Playwright, CI, git + remote, Vercel link, стили игрового режима, дизайн-токены.
2. SVG-конвейер: парсинг, санитизация, сегментация + тесты на фикстурах; три базовых арта.
3. Движок раскраски (локально): слои, карта меток, карандаш/кисть/резинка, удержание, прогресс, pointer events, экспорт/share, zoom/pan.
4. БД и вход: Drizzle + Neon, миграции, сиды, вход по стране + username, сессии, вход в админку, guards, rate limit.
5. Галерея: keyset API, карточки с рамкой прогресса, импорт/удаление, «начать заново», состояния.
6. UI редактора: панели инструментов и цветов с анимациями, рамка прогресса, 100% + встряска, reduced-motion.
7. История и синхронизация: ops, undo/redo, чекпоинты, офлайн-очередь, индикатор, продолжение после перезагрузки.
8. Аналитика + админка.
9. Полировка, адаптив, e2e, README, прод-деплой, `/coloring-review full`.

Если не успеваем, первой упрощаем визуальную часть админки. Движок, историю и синхронизацию не режем.

## Стек
- **Nuxt 4 + TypeScript strict**, pnpm 10, Node 24 (`.nvmrc`). TypeScript закреплён на 6.x: vue-tsc пока не работает с TS 7 (нативный порт).
- **Линт:** `@nuxt/eslint` (flat config, stylistic; Prettier не используем), **Stylelint** (`stylelint-config-standard-scss` + `stylelint-config-recommended-vue`).
- **Стили:** SCSS, scoped, дизайн-токены в CSS-переменных. Анимации на чистом CSS и встроенных средствах Vue, без библиотек анимаций.
- **Состояние:** Pinia для сессии, галереи и UI-состояния редактора. Движок раскраски живёт как нереактивный TS-класс (`markRaw`/`shallowRef`) и никогда не попадает в глубокую реактивность.
- **Валидация:** zod. Схемы и доменные типы лежат в `shared/` и используются клиентом и сервером.
- **Сервер:** Nitro server routes. **БД:** Neon Postgres + Drizzle (`@neondatabase/serverless`, `drizzle-orm/neon-http`). Локально подключаемся к ветке Neon `dev`, в проде к `main`, для PR создаются preview-ветки через интеграцию Vercel. Автотесты сервера работают на PGlite.
- **Файлы:** Vercel Blob (снимки состояния, миниатюры).
- **Сессии:** `nuxt-auth-utils` (cookie httpOnly/secure/sameSite). **Заголовки безопасности:** `nuxt-security`.
- **Тесты:** Vitest (+ `@nuxt/test-utils`), Playwright.
- **Деплой:** Vercel (пресет Nitro, Fluid Compute / Node). Edge runtime не используем.

## Архитектура
```
nuxt.config.ts        корень: только инструменты (eslint, test-utils); продуктового кода в корне нет
layers/core/          общая платформа: app.vue, стили «игрового режима» и токены, реестр игр,
                      auth/сессия, UI-кит, аналитика, админ-оболочка, хранилище
  app/                assets/styles, components, composables, pages, plugins, app.config.ts
  server/             api/auth, api/admin/*, db (drizzle schema, migrations), utils (requireUser/requireAdmin)
layers/coloring/      мини-игра «Раскраска»
  shared/             чистый TS для клиента и сервера: index.ts, art/ (schema.ts — формат арта), svg/ (конвейер импорта), types/
  app/engine/         canvas-движок (только клиент): render, hit-test, history, progress
  app/ (pages, components, app.config.ts)   server/api/coloring/*, server/assets/arts (базовые SVG)
shared/               zod-схемы, доменные типы и утилиты (types/, utils/) для клиента и сервера
tests/                unit (node), nuxt (environment nuxt), e2e (Playwright), fixtures/svg
```
- Игры регистрируются в `app.config.ts` своего слоя: `games.<id>: GameDefinition` (тип в `shared/types/game.ts`). Nuxt мержит app config всех слоёв, core читает реестр через `useGames()`.
- Код вне `app/`, `server/` и `shared/` слоя не попадает ни в один tsconfig и не проверяется typecheck, поэтому кладём его только в эти папки. `shared/` слоя не автоимпортируется (кроме `shared/utils`, `shared/types`), импорты явные.
- `shared/types` игрового слоя исключён из автоимпорта Nuxt и Nitro (хуки `imports:dirs` и `nitro:config` в `layers/coloring/nuxt.config.ts`). Типы игры не глобальные, core их не видит.
- В конфиге слоя `~` указывает на корень, а не на слой. Пути к файлам слоя строим через `new URL(path, import.meta.url)`.
- **Зависимости идут только `игра → core`.** Core не импортирует игры, игры не импортируют друг друга (правило ESLint `no-restricted-imports`).
- Новая мини-игра = новый layer в `layers/<game>/` + регистрация. Код core при этом не трогаем.
- SSR включён для входа и галереи. Редактор и админка работают только на клиенте (`routeRules: { ssr: false }`).

## Организация кода
- **Модуль = папка с `index.ts`.** Это его публичный вход: снаружи импортируем только из `index.ts`. Внутренние файлы (парсеры, хелперы) в индекс не выставляем, их импортируют напрямую только их тесты.
- **zod-схемы лежат в `schema.ts`** внутри модуля (`shared/art/schema.ts`). **Типы лежат в подпапке `types/`** (`shared/types/art.ts`, `shared/types/index.ts`). Типы данных выводятся из схем через `z.infer`, руками не дублируются.
- **Константы модуля лежат в `constants.ts`**, тексты для пользователя в `messages.ts`.
- **Страницы тонкие.** Состояние и логика живут в composable (`app/composables/useXxx.ts`), повторно используемая разметка в компоненте (`app/components`). Страница только собирает их вместе. Composables и компоненты Nuxt импортирует сам, `index.ts` им не нужен.
- **Ошибки для пользователя на русском.** Ошибки предметной области (импорт SVG и т. п.) идут как код плюс сообщение из `messages.ts`. Ошибки валидации zod: глобально включаем `z.config(z.locales.ru())` (на сервере и клиенте), для полей форм пишем свои сообщения прямо в схеме. API отдаёт ошибки в едином формате `{ code, message, fields? }`. Сырые сообщения zod и стектрейсы клиенту не уходят.

## Ключевые решения
**SVG-конвейер** (одинаков для импорта пользователем и для админки, выполняется на сервере):
- Лимиты: ≤ 1 МБ, ≤ 3000 элементов, ≤ 500 сегментов, таймаут. `@xmldom/xmldom` без DTD и entities.
- Фигуры → `d`, transform запекаются (`svgpath`). Светлые заливки и замкнутые контуры без заливки становятся **регионами** (`region`), тёмные заливки (яркость ≤ 0.2) и все обводки становятся **ink**. Первая фигура на весь холст (заливка фрейма Figma) превращается в регион-фон, а если её нет, фон синтезируется из viewBox. Учитываем `fill-rule="evenodd"`, CSS-классы из `<style>`, игнорируем clipPath фрейма Figma, разворачиваем только локальные `<use>`.
- **Исходная разметка SVG не рендерится никогда.** Храним нормализованный JSON `{version, viewBox, items[]}` (`layers/coloring/shared/art/schema.ts`): элементы `region | ink` в исходном z-порядке, `d` проверяется по whitelist.
- **Рендер:** арт (регионы белые, ink в своих цветах, исходный порядок) рисуется один раз и накладывается на слой краски через `multiply`. Поэтому контур всегда поверх краски без потери z-порядка и без швов.
- **Ограничение:** регион задаёт замкнутая фигура. Линии, которые визуально делят фигуру, отдельных регионов не создают (нужен flood-fill по растру). Записать в README.
- Проверить конвейер вручную можно на странице `/coloring/lab`.
- Неподдерживаемое (text, image, градиенты, маски, фильтры) пропускаем с предупреждением. Если сегментов 0, показываем понятную ошибку.

**Движок** (Canvas 2D, `layers/coloring/app/engine/`, только клиент; чистая логика вынесена в модули без DOM и покрыта юнит-тестами):
- Слои: paint-канвас (краска на белом фоне контента) и арт поверх (`ArtPreview`, вектор) с `mix-blend-mode: multiply` + `isolation: isolate`.
- Разрешение paint фиксированное, `PAINT_LONG_SIDE = 2048` по длинной стороне. От DPR оно не зависит: память предсказуема на iOS, зум до ~2× остаётся чётким, экспорт идёт тем же разрешением.
- Хит-тест: `isPointInPath` по регионам сверху вниз с префильтром по bbox, только на `pointerdown`. Ink для попадания прозрачен.
- Штрих ограничен **маской региона**: регион минус регионы выше по z-order, кешируется последняя. Каждый фрагмент рисуется на scratch-канвас, умножается на маску (`destination-in`) и только потом композится в paint (резинка через `destination-out`). Линия физически не выходит из региона.
- Операции хранятся в целочисленной сетке `OP_GRID = 4096` по длинной стороне арта (`layers/coloring/shared/ops`). Формат не зависит от разрешения рендера.
- Pointer Events + `getCoalescedEvents` + батчинг в `rAF`. В простое `rAF` не работает.
- Удержание: 450 мс, допуск 6 px; заливает или очищает регион. Второй палец отменяет текущий штрих (восстановление из бэкапа региона) и включает pinch/pan. Ctrl+колесо и pinch тачпадом дают зум, колесо при зуме двигает арт.
- Карандаш: тонкий, зернистая текстура (`createPattern`, детерминированный шум). Кисть: широкая, мягкий край (штампы радиального градиента с шагом по длине, `StampWalker` переносит остаток между фрагментами).
- **Прогресс**: сетка ~256 по длинной стороне. Карта меток рисуется один раз (регионы кодами-хешами, ink поверх как «нет региона»), поэтому под глазами и контурами ничего не считается. Обновление идёт только по dirty-rect штриха. Регион засчитывается при покрытии ≥ 95%, 100% показывается только когда готовы все. Фон в прогресс не входит.
- Replay операций визуально совпадает с живым рисованием, но не побитово (сглаживание на стыках фрагментов). Для undo это допустимо.
- Замер: кадр рисования в среднем 0.2 мс на GPU (бюджет 8 мс). Проверочная страница `/coloring/sandbox`.

**История и синхронизация:**
- Операции `stroke | fill | clear` (точки int16, упрощение RDP), курсор undo/redo, новая операция отрезает redo-ветку.
- Чекпоинты каждые 25 операций, поэтому стоимость undo не зависит от длины истории.
- Сервер: `ops(progress_id, seq)`, `cursor`, снимок и миниатюра в Blob. При загрузке берём снимок и догоняем хвост.
- Офлайн-очередь в IndexedDB, батчи, идемпотентность по `(progress_id, seq)`, retry с backoff, индикатор сохранения, `beforeunload`. Конфликт двух вкладок даёт 409, после чего клиент перезагружает состояние.
- «Начать заново» создаёт новую попытку (`progress.attempt`), старая попытка сохраняется.

**Пользователи и админ:**
- Username уникален глобально без учёта регистра, страна это атрибут (при несовпадении показываем «ник занят»).
- Вход в админку по одному логину и паролю из env. Каждый admin-эндпоинт проверяет `requireAdmin` на сервере.
- Все запросы к артам, прогрессу и истории проверяют владельца (IDOR).
- Лимит 20 импортов на пользователя.

**Аналитика:** события `open | start | complete | restart` пишутся на сервере, `start` и `complete` идемпотентны на попытку. Сторонних трекеров нет. На экране входа показываем уведомление о хранимых данных.

**Экспорт:** картинку собирает движок на offscreen-canvas 2048 px без UI. Blob готовим заранее, потому что Safari требует вызывать `share` синхронно в клике. Если `navigator.share({files})` недоступен, скачиваем файл.

## Интерфейс и игровой режим
- **Mobile-first:** базовые стили для телефона, расширяем только через `min-width`-медиа и container queries. `max-width`-медиа не используем.
- Основная ориентация **альбомная** (по макету). В портретной показываем экран «Поверните устройство». Адаптив под портрет может понадобиться позже, поэтому layout держим на переменных.
- `user-select:none`, `-webkit-touch-callout:none`, `touch-action:none` на холсте, `overscroll-behavior:none`, `position:fixed` + `100dvh`, отменяем `contextmenu`/`gesturestart`, `viewport-fit=cover`, `env(safe-area-inset-*)` со всех сторон (Dynamic Island в альбомной ориентации находится сбоку).
- Анимации только по `transform`/`opacity`, короткие (≤ 250 мс на последовательности), ввод не блокируют. Вся анимация учитывает `prefers-reduced-motion`.
- Выбранные инструмент и цвет должны читаться без подписей, при этом `aria-label` обязательны.
- Дизайн берём из Figma (файл `KybgvXCexjO9ixaz2pIUva`, Figma MCP). Отклонения от макета записываем в README.

## Бюджеты производительности
JS начальной страницы ≤ 150 КБ gzip. Движок грузится лениво только в редакторе. Кадр рисования ≤ 8 мс на среднем телефоне. Undo на истории из 1000 операций ≤ 16 мс. Память не растёт с длиной истории.

## README (к сдаче)
Обязательные разделы: локальный запуск; структура и архитектура; модель хранения состояния и истории; известные ограничения; решения и допущения; отклонения от макета; что сделано с ИИ и как проверялось; что улучшить; доступы (демо-пользователи, админ).
