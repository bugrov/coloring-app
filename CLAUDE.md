# Coloring App: веб-раскраска на Nuxt 4

Тестовое задание: детская раскраска (галерея, импорт SVG, раскрашивание по сегментам, история на сервере, аналитика, админка). Срок 3 рабочих дня. Подробный план и обоснования лежат в `docs/PLAN.md`: файл локальный и в git не входит. Если его нет, ориентируемся на этот документ.

Общение с пользователем и тексты коммитов и PR пишем **на русском**. Код, идентификаторы и комментарии в коде пишем на английском.

## Порядок работы (обязательно)
Работаем строго по шагам MVP (список ниже). Каждый шаг проходит один и тот же цикл:
1. Ветка `step-N-<name>` от `main`.
2. Реализация небольшими коммитами (conventional commits: `feat:`, `fix:`, `chore:`, `test:`, `docs:`, `refactor:`).
3. Автопроверки: `pnpm typecheck && pnpm lint && pnpm lint:css && pnpm test && pnpm build`, на UI-шагах ещё `pnpm test:e2e`.
4. Ревью: `/coloring-review step` проводит весь конвейер ревью (см. скилл): свой чек-лист → `code-review` по диффу → агент `code-simplifier` по изменённым файлам → `security-review` на шагах с вводом, файлами, сервером и правами. `security-guidance` (хук) и `typescript-lsp` работают в фоне сами.
5. Push → PR → Vercel preview.
6. **СТОП.** Отчёт пользователю: что сделано, результаты проверок, находки ревью, ссылка на preview, как проверить руками, какие решения приняты.
7. Ждём **явного «ОК»**. Без него не мержим и не начинаем следующий шаг. Замечания исправляем в той же ветке и повторяем пункты 3–6.
8. После ОК: merge без squash (история нужна полная), затем следующий шаг.

Дополнительные правила:
- Неоднозначность, которая не блокирует работу, решаем сами разумным способом и записываем в README («Решения и допущения») и в отчёт шага. Если вопрос блокирует работу, спрашиваем пользователя.
- Не расширяем объём работы шага без согласования. Мелкие находки вне шага записываем в отчёт.
- Секреты храним только в `.env` и в Vercel env. В репозиторий кладём `.env.example`.
- Не пушим в `main` напрямую и не делаем force-push.
- **База данных и авторизация: только решения из официальной документации** (Drizzle, Neon, nuxt-auth-utils, nuxt-security, h3), собственные «изобретения» здесь не допускаются. Если документация молчит или версия модуля с ней расходится, останавливаемся и сообщаем пользователю, не придумываем обход молча. К **настоящей базе** (миграции, сиды, e2e с базой) без явного подтверждения пользователя не обращаемся, тесты серверной логики идут на PGlite.

## Шаги MVP
0. Подготовка: план, `CLAUDE.md`, скилл ревью, доступ к Figma (MCP), вопросы техлиду.
1. Скелет: Nuxt 4, layers, TS strict, ESLint, Stylelint, Vitest, Playwright, CI, git + remote, Vercel link, стили игрового режима, дизайн-токены.
2. SVG-конвейер: парсинг, санитизация, сегментация + тесты на фикстурах; три базовых арта.
3. Движок раскраски (локально): слои, карта меток, карандаш/кисть/резинка, удержание, прогресс, pointer events, экспорт/share, zoom/pan.
4. БД и вход: Drizzle + Neon, миграции, сиды, вход по стране + username, сессии, вход в админку, guards, rate limit.
4а. **Мини-шаг (перед шагом 5): именованные маршруты.**
   - Каждая страница объявляет `definePageMeta({ name: ..., auth: ... })` с понятным именем.
   - Имена маршрутов лежат в константах: объект `as const` на слой в `layers/<слой>/shared/routes.ts` (не enum). У `core` свои имена (вход, главная, админка), у каждой игры свои: core не импортирует имена игр. Пример: `definePageMeta({ name: CoreRoutes.LOGIN, auth: 'public' })`.
   - Имена строчными словами через дефис (`login`, `admin-login`, `coloring-gallery`), как их генерирует Nuxt, чтобы ссылки не ломались.
   - Все редиректы, ссылки и `navigateTo` переводим на именованные (`{ name: CoreRoutes.LOGIN }`), строковых путей в коде не остаётся; реестр игр (`GameDefinition.entry`) хранит имя маршрута. Не даём вернуть строковый путь: проверка в ESLint или тест.
   - **Ник уникален парой (ник, страна)** (ответ техлида): одинаковый ник в разных странах — разные игроки. Миграция по правилу двух деплоев: добавить составной unique-индекс `(username_key, country)`, в следующем релизе убрать старый unique по `username_key`. `signIn` ищет по паре, `onConflictDoNothing` целится в новый индекс. Ошибка `username_taken`, её сообщение, тесты, e2e и текст в README убираем.
5. Галерея: keyset API, карточки с рамкой прогресса (старт в точке 180° = слева, против часовой), импорт/удаление, «начать заново» (остаётся), состояния.
6. UI редактора: панели инструментов и цветов с анимациями, рамка прогресса, 100% + встряска, reduced-motion.
   - Заливка удержанием остаётся мгновенной, но с анимацией: кольцо-индикатор у пальца, затем круговое раскрытие цвета ~250 мс; при reduced-motion мгновенно.
   - **Прозрачность** (ответ техлида): пресеты 100 / 75 / 50 / 25 %. Пока закладываем кнопку-переключатель; куда её поместить (на панель или в попап) решим позже. Прозрачность — параметр операции (карандаш, кисть, заливка удержанием); штрих рисуется непрозрачным на scratch и композится с `globalAlpha`, поэтому перекрытия внутри одного штриха не темнеют. Резинка стирает полностью. Полупрозрачная краска засчитывается как закрашенная от ≥ 25 % (порог альфы в подсчёте прогресса меняется).
7. История и синхронизация: ops, undo/redo, чекпоинты, офлайн-очередь, индикатор, продолжение после перезагрузки.
   - Лимит undo: константа **100** шагов, подтверждаем нагрузочным замером на 100 операциях до фиксации.
   - Синхронизацию между устройствами и вкладками сначала проектируем и обсуждаем с пользователем, только потом реализуем.
8. Аналитика + админка.
   - Допуск «закрашено» (сейчас 95 %) — глобальная настройка в админке, фолбэк 95 %, если не задана.
   - Палитра: по возможности редактируется в админке (опционально).
9. Полировка, адаптив, e2e, README, прод-деплой, `/coloring-review full`.

Если не успеваем, первой упрощаем визуальную часть админки. Движок, историю и синхронизацию не режем.

## Стек
- **Nuxt 4 + TypeScript strict**, pnpm 10, Node 24 (`.nvmrc`). TypeScript закреплён на 6.x: vue-tsc пока не работает с TS 7 (нативный порт).
- **Линт:** `@nuxt/eslint` (flat config, stylistic; Prettier не используем), **Stylelint** (`stylelint-config-standard-scss` + `stylelint-config-recommended-vue`).
- **Стили:** SCSS, scoped, дизайн-токены в CSS-переменных. Анимации на чистом CSS и встроенных средствах Vue, без библиотек анимаций.
- **Состояние:** Pinia для сессии, галереи и UI-состояния редактора. Движок раскраски живёт как нереактивный TS-класс (`markRaw`/`shallowRef`) и никогда не попадает в глубокую реактивность.
- **Валидация:** zod. Схемы и доменные типы лежат в `shared/` и используются клиентом и сервером.
- **Сервер:** Nitro server routes. **БД:** Neon Postgres + Drizzle (`@neondatabase/serverless`, `drizzle-orm/neon-http`). Локально подключаемся к ветке Neon `dev`, в проде к `main`, для PR создаются preview-ветки через интеграцию Vercel. Автотесты сервера работают на PGlite.
- **Файлы:** Vercel Blob (снимки состояния, миниатюры).
- **Сессии:** `nuxt-auth-utils`: шифрованная cookie (`httpOnly`, `secure`, `sameSite=lax`), пароль `NUXT_SESSION_PASSWORD` ≥ 32 символов, срок жизни 30 дней. В `user` лежит то, что видит клиент, в `secure` (только сервер) роль, которой доверяет сервер. Вход заменяет сессию целиком (`replaceUserSession`), выход и чтение сессии на клиенте даёт сам модуль (`useUserSession`, `/api/_auth/session`, этот путь нельзя перехватывать middleware).
- **Заголовки безопасности:** `nuxt-security` (CSP с nonce, HSTS, `X-Frame-Options` и др. по умолчанию). Его rate limiter хранит счётчики в памяти одного экземпляра сервера и по документации не годится для сложного продакшена: включён только для маршрутов входа (пользователь 60 за 5 мин с IP, админ 5 за 5 мин), надёжный вариант — внешнее хранилище. Клиент определяется по `x-forwarded-for` (на Vercel его выставляет платформа). XSS-валидатор по умолчанию проверяет тела POST и заблокирует загрузку SVG: для маршрутов импорта (шаги 5 и 8) его отключаем через `routeRules`.
- **Временное закрепление `xss@1.0.15`** в `pnpm-workspace.yaml`: `nuxt-security` 2.6.0 с `xss` 1.0.16 падает (`escapeHtml is not a function`, каждый POST даёт 500), исправление ждёт слияния ([PR #765](https://github.com/Baroshem/nuxt-security/pull/765)). Снять закрепление, когда выйдет версия с поддержкой.
- **Миграции применяются в сборке Vercel:** `vercel.json` → `buildCommand: "pnpm db:migrate && pnpm build"` (документированный способ интеграции Neon: превью получает схему в своей ветке БД, продакшен — в `main`). Упавшая миграция останавливает деплой. Поэтому **миграции обратно совместимы с предыдущей версией кода**: только добавляем (новые таблицы, колонки с default или nullable); удаление и переименование делаем в два деплоя.
- **Переменные Vercel:** интеграция Neon сама создаёт `DATABASE_URL` и `DATABASE_URL_UNPOOLED`. Вручную для Production и Preview: `NUXT_SESSION_PASSWORD` (≥ 32 символов, свой для каждого окружения), `NUXT_ADMIN_LOGIN`, `NUXT_ADMIN_PASSWORD`.
- **Конфигурация сервера через `runtimeConfig`** (документация Nuxt): ключи объявлены в `nuxt.config`, значения подставляются переменными `NUXT_<КЛЮЧ>`, читаются через `useRuntimeConfig(event)`. Nuxt приводит значения к типам (`destr`): пароль вида `4848e0` придёт числом, поэтому не-строка считается «не настроено» и вход отключается. Исключение — `DATABASE_URL`: его имя задаёт интеграция Neon, а `runtimeConfig` с другим именем переменной ломается в рантайме, поэтому он читается из `process.env`.
- **Журнал безопасности:** `layers/core/server/utils/audit.ts` пишет одну JSON-строку на событие (вход администратора: успех, отказ, не настроен) с адресом и временем, без введённого пользователем. `nuxt-security` по умолчанию вырезает весь `console` из сборки, поэтому `removeLoggers: false`, а правило ESLint `no-console` не пускает логи куда-либо ещё.
- **Drizzle:** стабильная ветка `latest` (0.45), документация описывает RC 1.0, используемые вызовы совпадают. Драйвер `neon-http` не поддерживает интерактивные транзакции, поэтому сервисы используют одиночные запросы. Приложение работает через pooled `DATABASE_URL`, миграции через прямой `DATABASE_URL_UNPOOLED` (требование Neon). `.env` в `drizzle-kit` подаёт Node (`--env-file-if-exists=.env`), без `dotenv`.
- **Тесты:** Vitest (+ `@nuxt/test-utils`), Playwright.
- **Деплой:** Vercel (пресет Nitro, Fluid Compute / Node). Edge runtime не используем.

## Архитектура
```
nuxt.config.ts        корень: только инструменты (eslint, test-utils); продуктового кода в корне нет
layers/core/          общая платформа: app.vue, стили «игрового режима» и токены, реестр игр,
                      auth/сессия, UI-кит, аналитика, админ-оболочка, хранилище
  app/                assets/styles, components, composables, pages, plugins, app.config.ts
  server/             api/auth, api/admin/*, db (drizzle schema, migrations), utils (requireUser/requireAdmin)
layers/coloring/      мини-игра «Раскраска»
  shared/             чистый TS для клиента и сервера: index.ts, art/ (schema.ts — формат арта), svg/ (конвейер импорта), types/
  app/engine/         canvas-движок (только клиент): render, hit-test, history, progress
  app/ (pages, components, app.config.ts)   server/api/coloring/*, server/assets/arts (базовые SVG)
shared/               zod-схемы, доменные типы и утилиты (types/, utils/) для клиента и сервера
tests/                unit (node), nuxt (environment nuxt), e2e (Playwright), fixtures/svg
```
- Игры регистрируются в `app.config.ts` своего слоя: `games.<id>: GameDefinition` (тип в `shared/types/game.ts`). Nuxt мержит app config всех слоёв, core читает реестр через `useGames()`.
- Код вне `app/`, `server/` и `shared/` слоя не попадает ни в один tsconfig и не проверяется typecheck, поэтому кладём его только в эти папки. `shared/` слоя не автоимпортируется (кроме `shared/utils`, `shared/types`), импорты явные.
- `shared/types` игрового слоя исключён из автоимпорта Nuxt и Nitro (хуки `imports:dirs` и `nitro:config` в `layers/coloring/nuxt.config.ts`). Типы игры не глобальные, core их не видит.
- В конфиге слоя `~` указывает на корень, а не на слой. Пути к файлам слоя строим через `new URL(path, import.meta.url)`.
- **Зависимости идут только `игра → core`.** Core не импортирует игры, игры не импортируют друг друга (правило ESLint `no-restricted-imports`).
- Новая мини-игра = новый layer в `layers/<game>/` + регистрация. Код core при этом не трогаем.
- SSR включён для входа и галереи. Редактор и админка работают только на клиенте (`routeRules: { ssr: false }`).

## Организация кода
- **Модуль = папка с `index.ts`.** Это его публичный вход: снаружи импортируем только из `index.ts`. Внутренние файлы (парсеры, хелперы) в индекс не выставляем, их импортируют напрямую только их тесты.
- **zod-схемы лежат в `schema.ts`** внутри модуля (`shared/art/schema.ts`). **Типы лежат в подпапке `types/`** (`shared/types/art.ts`, `shared/types/index.ts`). Типы данных выводятся из схем через `z.infer`, руками не дублируются.
- **Константы модуля лежат в `constants.ts`**, тексты для пользователя в `messages.ts`.
- **Компоненты раскладываем по папкам по смыслу** (`components/auth`, `components/form`, `components/(shell)`). По документации Nuxt имя компонента строится из пути, повторяющиеся сегменты убираются (`auth/AuthForm.vue` остаётся `<AuthForm>`), а папка в круглых скобках в имя не входит (`(shell)/SafeAreaPage.vue` остаётся `<SafeAreaPage>`). Имя файла совпадает с именем компонента. `index.ts` в `components/` не нужен: компоненты импортируются автоматически, а лишний `.ts` сканер мог бы принять за компонент. Папку заводим, когда в группе больше одного компонента.
- **Страницы тонкие.** Состояние и логика живут в composable (`app/composables/useXxx.ts`), повторно используемая разметка в компоненте (`app/components`). Страница только собирает их вместе. Composables и компоненты Nuxt импортирует сам, `index.ts` им не нужен.
- **Ошибки для пользователя на русском.** Ошибки предметной области (импорт SVG и т. п.) идут как код плюс сообщение из `messages.ts`. Ошибки валидации zod: глобально включаем `z.config(z.locales.ru())` (на сервере и клиенте), для полей форм пишем свои сообщения прямо в схеме. API отдаёт ошибки в едином формате `{ code, message, fields? }`. Сырые сообщения zod и стектрейсы клиенту не уходят.

## Ключевые решения
**SVG-конвейер** (одинаков для импорта пользователем и для админки, выполняется на сервере):
- Лимиты: ≤ 1 МБ, ≤ 3000 элементов, ≤ 500 регионов, ≤ 3000 элементов результата и ≤ 2 МБ path-данных, CSS ≤ 64 КБ, вложенность ≤ 256, обходы с `<use>` ≤ 20 × элементов, обработанные path-данные ≤ 2 × размера файла + 64 КБ, результат ≤ 4 × размера файла + 64 КБ, viewBox в разумных пределах (соотношение сторон ≤ 20), таймаут 2 с. `@xmldom/xmldom` без DTD и entities. Разбор CSS — линейный сканер, без регулярок по недоверенному тексту. Детали предупреждений очищены до безопасного алфавита.
- **Для сервера (шаги 4–5):** rate limit на импорт и загрузку в админке (неудачные попытки тоже стоят CPU), загрузку декодировать через `new TextDecoder('utf-8', { fatal: true })` и отклонять не-UTF-8.
- `transform` разбирается своим линейным парсером в матрицу (один раз на элемент), path-данные — своим линейным токенизатором в явные команды, затем один проход `svgpath` на фигуру. Регулярки и неявные повторы `svgpath` на недоверенных данных квадратичны, поэтому их не используем. Выход `d` всегда с явными командами.
- Фигуры → `d`, transform запекаются. Светлые заливки и замкнутые контуры без заливки становятся **регионами** (`region`), тёмные заливки (яркость ≤ 0.2) и все обводки становятся **ink**. Первая фигура на весь холст (заливка фрейма Figma) превращается в регион-фон, а если её нет, фон синтезируется из viewBox. Учитываем `fill-rule="evenodd"`, CSS-классы из `<style>`, игнорируем clipPath фрейма Figma, разворачиваем только локальные `<use>`.
- **Исходная разметка SVG не рендерится никогда.** Храним нормализованный JSON `{version, viewBox, items[]}` (`layers/coloring/shared/art/schema.ts`): элементы `region | ink` в исходном z-порядке, `d` проверяется по whitelist. Формат версии 2: у регионов хранятся `bounds` (считаются при импорте, округлены наружу, проверяется `min ≤ max`), поэтому клиент пути не разбирает и `svgpath` в бандл движка не попадает.
- **Рендер:** арт (регионы белые, ink в своих цветах, исходный порядок) рисуется один раз и накладывается на слой краски через `multiply`. Поэтому контур всегда поверх краски без потери z-порядка и без швов.
- **Ограничение:** регион задаёт замкнутая фигура. Линии, которые визуально делят фигуру, отдельных регионов не создают (нужен flood-fill по растру). Записать в README.
- Проверить конвейер вручную можно на странице `/coloring/lab`.
- Неподдерживаемое (text, image, градиенты, маски, фильтры) пропускаем с предупреждением. Если сегментов 0, показываем понятную ошибку.

**Движок** (Canvas 2D, `layers/coloring/app/engine/`, только клиент; чистая логика вынесена в модули без DOM и покрыта юнит-тестами):
- Слои: paint-канвас (краска на белом фоне контента) и арт поверх (`ArtPreview`, вектор) с `mix-blend-mode: multiply` + `isolation: isolate`.
- Разрешение paint фиксированное, `PAINT_LONG_SIDE = 2048` по длинной стороне. От DPR оно не зависит: память предсказуема на iOS, зум до ~2× остаётся чётким, экспорт идёт тем же разрешением.
- Хит-тест: `isPointInPath` по регионам сверху вниз с префильтром по bbox, только на `pointerdown`. Ink для попадания прозрачен.
- Штрих ограничен **маской региона**: регион минус регионы выше по z-order. Кеш на 2 маски (LRU): чаще всего чередуются объект и фон, а маска фона самая дорогая. Каждый фрагмент рисуется на scratch-канвас, умножается на маску (`destination-in`) и только потом композится в paint (резинка через `destination-out`). Линия физически не выходит из региона.
- Операции хранятся в целочисленной сетке `OP_GRID = 4096` по длинной стороне арта (`layers/coloring/shared/ops`). Формат не зависит от разрешения рендера.
- Pointer Events + `getCoalescedEvents` + батчинг в `rAF`. В простое `rAF` не работает. Нажатия на пустые полосы вокруг рисунка игнорируются, повторы одной точки отбрасываются. Без постоянного `will-change: transform` на контенте, иначе вектор размывается при зуме.
- Удержание: 450 мс, допуск 6 px; заливает или очищает регион. Второй палец включает pinch/pan, Ctrl+колесо и pinch тачпадом дают зум (шаг колеса ограничен, щелчок ≈ ×1.28), колесо при зуме двигает арт.
- Незавершённый штрих (второй палец, `pointercancel`): короткий откатывается из бэкапа региона, очень длинный (уже разрезанный на операции) сохраняется целиком. При смене арта или размонтировании штрих просто выбрасывается.
- Перо: пока рисует перо, касания пальцами игнорируются; касание пером сбрасывает уже лежащие пальцы (ладонь).
- Потерянные `pointerup`: `lostpointercapture` самой сцены обрабатывается как отмена (событие всплывает, поэтому цель проверяется); новый primary-указатель сбрасывает все зависшие, а начатый штрих сохраняет; повторное нажатие тем же указателем сначала коммитит прежний штрих.
- Карандаш: тонкий, **непрозрачная** зернистая текстура (`createPattern`, детерминированный шум, осветление к белому). Непрозрачность важна: перекрытия штриха не темнеют. Кисть: широкая, мягкий край (штампы радиального градиента с шагом по длине, `StampWalker` переносит остаток между фрагментами).
- **Прогресс**: сетка ~256 по длинной стороне. Карта меток (`Int32Array`) рисуется один раз (регионы кодами-хешами, ink поверх как «нет региона» с теми же lineCap/lineJoin, что и экспорт), поэтому под глазами и контурами ничего не считается. Обновление идёт только по dirty-rect штриха: ячейка закрашена, если закрашена хотя бы половина из 16 пикселей-образцов её блока 8×8 (считаем сами по `getImageData`, а не уменьшением через `drawImage`, фильтрация которого отличается в браузерах). Регион засчитывается при покрытии ≥ 95%, 100% показывается только когда готовы все. Фон в прогресс не входит.
- Replay совпадает с живым рисованием: линейные инструменты каждый кадр восстанавливают основу из бэкапа и перерисовывают путь в dirty-rect (только сегменты рядом с ним, поэтому кадр не дорожает с длиной штриха), кисть переносит шаг штампов, длинные штрихи режутся на операции прямо во время рисования. Путь с ошибкой сохраняет валидную часть до неё (как в браузерах). Остаются только различия в сглаживании кромки (альфа ±2–60 на крайних пикселях, их растеризует Skia), визуально незаметно.
- Движок освобождает offscreen-канвасы (`dispose()`) при смене арта и размонтировании. Холсты экспорта живут только на время экспорта.
- Замер: кадр рисования в среднем 0.2 мс на GPU (бюджет 8 мс). Проверочная страница `/coloring/sandbox`.

**История и синхронизация:**
- Операции `stroke | fill | clear` (точки int16, упрощение RDP), курсор undo/redo, новая операция отрезает redo-ветку.
- Чекпоинты каждые 25 операций, поэтому стоимость undo не зависит от длины истории.
- Сервер: `ops(progress_id, seq)`, `cursor`, снимок и миниатюра в Blob. При загрузке берём снимок и догоняем хвост.
- Офлайн-очередь в IndexedDB, батчи, идемпотентность по `(progress_id, seq)`, retry с backoff, индикатор сохранения, `beforeunload`. Конфликт двух вкладок даёт 409, после чего клиент перезагружает состояние.
- «Начать заново» создаёт новую попытку (`progress.attempt`), старая попытка сохраняется.

**Пользователи и админ:**
- Уникальна **пара (username без учёта регистра, страна)** (ответ техлида; до мини-шага 4а в коде ещё глобальная уникальность и «ник занят»). Разрешены латиница A–Z, кириллица, цифры, «_» и «-», 3–20 символов, **латиница и кириллица в одном имени не смешиваются** (иначе `Аnna` с кириллической «А» подделывает `Anna`). В ключе уникальности «ё» равна «е», отображаемое имя остаётся как введено. Остальные письменности и диакритика отклоняются: имя можно записать латиницей.
- Вход в админку по одному логину и паролю из env. Каждый admin-эндпоинт проверяет `requireAdmin` на сервере.
- Все запросы к артам, прогрессу и истории проверяют владельца (IDOR).
- Лимит 20 импортов на пользователя.

**Аналитика:** события `open | start | complete | restart` пишутся на сервере, `start` и `complete` идемпотентны на попытку. Сторонних трекеров нет. На экране входа показываем уведомление о хранимых данных.

**Экспорт:** картинку собирает движок на offscreen-canvas 2048 px без UI. Blob готовим заранее, потому что Safari требует вызывать `share` синхронно в клике. Если `navigator.share({files})` недоступен, скачиваем файл.

## Интерфейс и игровой режим
- **Mobile-first:** базовые стили для телефона, расширяем только через `min-width`-медиа и container queries. `max-width`-медиа не используем.
- Основная ориентация **альбомная** (по макету). В портретной показываем экран «Поверните устройство». Адаптив под портрет может понадобиться позже, поэтому layout держим на переменных.
- `user-select:none`, `-webkit-touch-callout:none`, `touch-action:none` на холсте, `overscroll-behavior:none`, `position:fixed` + `100dvh`, отменяем `contextmenu`/`gesturestart`, `viewport-fit=cover`, `env(safe-area-inset-*)` со всех сторон (Dynamic Island в альбомной ориентации находится сбоку).
- Анимации только по `transform`/`opacity`, короткие (≤ 250 мс на последовательности), ввод не блокируют. Вся анимация учитывает `prefers-reduced-motion`.
- Выбранные инструмент и цвет должны читаться без подписей, при этом `aria-label` обязательны.
- Дизайн берём из Figma (файл `KybgvXCexjO9ixaz2pIUva`, Figma MCP). Отклонения от макета записываем в README.

## Открытые вопросы к техлиду

0. **Вход без пароля и защита от подбора:** имя и страна — единственный ключ, лимит по IP слабый (см. README, ограничения). Пока: вход по ТЗ без пароля, лимит в памяти, CSRF нет.
